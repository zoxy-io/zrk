zrk 3.0.3 fixes two HTTP/3 interoperability failures: against haproxy every
request failed, and against envoy no connection completed its handshake.

```sh
brew upgrade zrk
```

## haproxy: a padded frame length is read

haproxy writes every HTTP/3 DATA frame's length as an eight-octet integer,
reserved before it knows how much body the frame will carry. RFC 9000 section
16 allows any encoding long enough for the value, and only a frame *type* must
be minimal. zrk's HTTP/3 layer (zoxy-io/h3) refused any non-minimal length as a
frame error, so each response from haproxy 3.4 closed its connection and
counted as a read error. The length is now read in any encoding; the type
check is unchanged.

## envoy: no SNI for an IP address

zrk put the target's host in the QUIC ClientHello's server_name extension even
when the host was an IP literal, which RFC 6066 section 3 does not permit.
envoy's QUIC stack (QUICHE) closes such a handshake with
`QUIC_HANDSHAKE_FAILED_INVALID_HOSTNAME`, so `zrk --http3` against envoy at an
IP address completed nothing. The extension is now left out for IPv4 and IPv6
literals, and sent as before for a name. Certificate verification still checks
the host. HTTP/1.1 and HTTP/2 over TLS are unchanged.

## Verified

`zrk --http3 -k` at an IP address, 50 connections at 500 requests/s for five
seconds, against zoxy 1.2.0, haproxy 3.4.8, nginx 1.31 and envoy 1.40: every
request completed, with no socket errors. Before this release, haproxy and envoy
completed none.

The h3 dependency moves from 8c55579 to zoxy-io/h3's main branch, which carries
the frame-length fix along with 139 other commits; zrk's tests pass on it.
