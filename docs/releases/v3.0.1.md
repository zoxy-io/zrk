A maintenance release: zrk now builds with Zig 0.17. The move also brings in
the fixes its dependencies have landed since 3.0.0, and one of those changes
what zrk reports. No flags, output fields or defaults change.

```sh
brew upgrade zrk
```

## HTTP/2 counts a malformed `content-length` as an error

zrk now records an HTTP/2 response as a `read` error, not a success, when its
`content-length` is not plain digits or when two `content-length` lines
disagree. RFC 9110 section 8.6 defines the field as `1*DIGIT`, and RFC 9113
section 8.1.1 calls a response with an invalid one malformed.

- The check comes from zoxy-io/h2's field validator, and it applies even though
  zrk otherwise reads response fields leniently.
- A value repeated identically, such as `content-length: 2` twice, is still
  accepted, as the RFC allows.
- `--http3` already applied the same rule. HTTP/1.1's parser already refused
  conflicting lengths.

Against a raw h2c server that answers every request with
`content-length: 2a`, `-R 50 -d 1s`:

|       | result                 |
| ----- | ---------------------- |
| 3.0.0 | 50 requests, no errors |
| 3.0.1 | `read: 50`             |

A server that sends these was never framing its responses correctly. 3.0.0
reported it as healthy.

## HTTP/3 loss recovery

Two fixes from zoxy-io/h3 change how a QUIC connection recovers from loss:

- **A lost window update is resent.** Packets carrying only `MAX_DATA`,
  `MAX_STREAM_DATA` or `MAX_STREAMS` were recorded as acknowledgement-only.
  Their loss started no timer, and could only be noticed once a later packet
  was acknowledged. When a window update was all a receiver had to send, the
  transfer could stall until the peer sent something else.
- **A packet is never sent without being recorded.** When the loss-recovery
  table was full, a packet went out untracked. If it was lost, nothing
  retransmitted its stream data, and the transfer stopped.

The known issues listed for 3.0.0 are unchanged. In particular, `--http3` is
still slow on large responses over a real network ([#89]).

[#89]: https://github.com/zoxy-io/zrk/issues/89

## A HelloRetryRequest is recognised

The QUIC handshake compares the server's `Random` with RFC 8446's
HelloRetryRequest value, so that a retry fails by name. That value is the
SHA-256 of "HelloRetryRequest", but zrk's copy had zeros for its second half,
so the comparison never matched.

What you see does not change. zrk offers one key-exchange group, X25519, so a
server that asks for a different one failed the connect before and fails it
now. It now fails at the check written for it, and a test holds the constant
to its definition.

## Building from source

zrk now needs Zig 0.17. `minimum_zig_version` is 0.17.0, and CI builds with
0.17.1, the version the Nix flake pins (`nix develop`, or `direnv allow`).
zio, the runtime under every connection, moves from 0.19.1 to 0.20.1.
zio's changelog lists fixes to cancellation and timeouts.

Embedders need Zig 0.17 too. The `zrk` module's API is unchanged.

- **Release builds:** the four release targets build in ReleaseFast.
- **`--version`:** the built binary reports 3.0.1.
- **Local servers:** with the Zig 0.17 build, every run completed with zero

  - TLS with `--disable-keepalive`, which exercises the end-of-stream path the

  all with zero errors:
  - HTTPS to example.com;
  - HTTP/2 to www.cloudflare.com;
  - HTTP/3 to cloudflare-quic.com.
