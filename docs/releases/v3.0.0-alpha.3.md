The third alpha of v3.0.0. Almost all of it is about one thing: what zrk
does when a server retires a connection it is using. Until now it counted
that as the server failing requests, and it wasn't.

**This is a prerelease.** It is not on the Homebrew tap and `brew upgrade` will
not offer it — the tap holds one formula and stable users read it. Take an
archive from the assets below.

## A server recycling connections is no longer a run of errors

Servers retire connections on purpose. nginx does it after 1,000 requests by
default (`keepalive_requests`), and so do most proxies and load balancers in
some form. They say so with a GOAWAY that names the last request they will
process, finish those, and close. Anything the client sent after that line was
never looked at, and both protocols say so explicitly — RFC 9114 §5.2 for
HTTP/3, RFC 9113 §6.8 for HTTP/2 — which makes it safe to send again.

zrk did not read that line. On HTTP/3 it ignored GOAWAY outright and kept
opening streams past it; on HTTP/2 it stopped opening streams but threw away
the identifier that said which of the open ones were safe. Either way, every
request past the line was charged as a read error, and on HTTP/3 the clean
close itself was one more. Against nginx at its defaults, 5 s runs:

| | HTTP/3 before | HTTP/2 before | now, both |
| --- | --- | --- | --- |
| `-R 240 -c 1` | 1 | 1 | 0 |
| `--closed -c 2` | — | 190 | 0 |
| `--closed -c 2 -s 8` | 927 | 1,593 | 0 |
| `--closed -c 4 -s 16` | 2,796 | 3,552 | 0 |

Those were errors on a server that was doing nothing wrong — 1.5% of the
last run — enough to trip a `--max-error-rate 0.01` gate.

Now zrk opens nothing after a GOAWAY, lets the requests the server accepted
finish, and sends the rest again on the next connection. The same goes for a
request the server rejects outright — `H3_REQUEST_REJECTED` or
`REFUSED_STREAM`, which carry the same guarantee. A retried request keeps the
time it was *scheduled* for, so its coordinated-omission latency still runs
from when it was due, and it does not advance the schedule. And it is retried
**once**: a server that declines everything shows up as errors, not as a run
that quietly reports nothing.

On HTTP/3 the replacement connection is opened at once, rather than after the
5 ms pause meant for a target refusing everything — at `-R 4000 -c 2 -s 16`
that took p99 from 3.5 ms to 0.3 ms.

**What this changes for you.** Under connection recycling, closed-loop tail
latency goes *up*. At `--closed -c 4 -s 16` over HTTP/2, p50 and p90 do not
move, and p99 goes from about 1.8 ms to about 4.5 ms. That is not a
regression. The ~1.5% of requests that used to be dropped as errors are now
measured, reconnect included, and 1.5% sits right on the p99 line — the old
number looked better because it left out exactly the requests that had to
wait for a new connection. Where no server sends GOAWAY, nothing changes.

## And a request that vanished

On multiplexed HTTP/2 there was a narrower version of the same fault. A request
that lost the race with a GOAWAY — the slot claimed, the stream not yet opened
when the GOAWAY landed — was dropped without a trace: the schedule had already
moved past it, the stream never opened, and nothing counted it. It is now
queued with the others and sent on the next connection.

## Smaller things

- **An oversized `--http3` request is a usage error again.** An HTTP/3 request
  has to fit one QUIC stream write (4 KiB, headers included). An inline
  `--body` over that was refused up front, but `-b @FILE` was read after the
  check, and the check left out the headers. Either way the run started and
  failed with exit 1 and `RequestTooLarge (try -k to skip TLS verification if
  this is certificate-related)` — a certificate hint for a size problem. It is
  now exit 2 and `the request is too large for --http3; its headers and --body
  must fit one QUIC stream write`.
- **`--disable-keepalive --http3` says `--http3`.** It was always refused, but
  the message and `--help` named only `--http2`.

## For embedders

`h2conn` is exported from the library root, and two things in it grew:

- `h2conn.Incoming` has a new `refused` variant, for a stream reset with
  `REFUSED_STREAM`. An exhaustive `switch` over it needs a case.
- `h2conn.Error` has a new `Refused`, and `Session.exchange` can return it.
  An exhaustive `switch` over the error needs a case too.

`Incoming.going_away` keeps its shape; the GOAWAY's last stream is on
`Session.peer_last_stream`. `runner.run`, which is what `docs/library.md`
documents, is unchanged.

## Known issues

- **`--http3` is slow on large responses over a real path.** Each stream's
  receive window is 16 KiB, so one stream moves at most 16 KiB per round trip.
  Over loopback that is invisible; at a 62 ms RTT, a 126 KB page takes 712 ms
  against HTTP/2's 109 ms, and a 1.3 MB one takes over 10 s — past the default
  `--timeout`. Until that changes, treat `--http3` latencies for responses
  beyond a few tens of KiB over a real network as zrk's, not the server's.
  Raising the window is not a one-line change, because it is also a
  compile-time buffer size that sets the memory per connection;
  [#89](https://github.com/zoxy-io/zrk/issues/89) has the measurements and
  the options.
- **ECDSA test certificates made with macOS's `/usr/bin/openssl`** are
  rejected by `--http3` even with `-k`. That binary is LibreSSL, which writes
  the curve's parameters out in full rather than naming the curve; RFC 5480
  requires the name, no real CA issues the other form, and the parser zrk uses
  refuses it. `--http2 -k` accepts the same certificate because it never
  parses one. Make test certificates with OpenSSL 3 instead
  (`/opt/homebrew/opt/openssl@3/bin/openssl` from Homebrew).

## Everything else

Unchanged from alpha.2: certificate verification on `--http3`, receive
batching, and every flag, report and gate.
