The second alpha of v3.0.0. Two changes to `--http3` that matter, and one of
them changes what a run needs to work.

**This is a prerelease.** It is not on the Homebrew tap and `brew upgrade` will
not offer it — the tap holds one formula and stable users read it. Take an
archive from the assets below.

## `--http3` verifies certificates, and no longer requires `-k`

In alpha.1 it refused to run without `--insecure`, because the QUIC TLS engine
parsed `Certificate` and `CertificateVerify` only far enough to keep the
transcript honest and then threw both away. It verifies now, the same way the
other two transports do: the chain builds to a system anchor and the name has
to match, through the same `tls.Trust` that serves zssl — one implementation of
zrk's trust decision rather than a second copy of it.

What is new rather than shared is RFC 8446 §4.4.3's `CertificateVerify`, the
half a chain cannot give you. A chain says somebody was issued a certificate
for the name; the signature says the peer holds its key. Without it, anyone
able to reach the client could replay a chain they do not own.

**What this changes for you.** `-k/--insecure` is now an opt-out, exactly as it
is elsewhere — so a command line that passed it still works. But a run that
*relied* on verification being absent will now fail: pointing `--http3` at a
self-signed or private-CA target needs `-k` explicitly, and a container without
a system trust store will fail where alpha.1 did not. Both are the behaviour
the other transports have always had.

Proven in both directions, because it is easy to ship something that only
claims to verify: against the interop suite's throwaway CA without `-k`, every
connection is refused and no request is sent; with `-k`, they all go through;
and against a public HTTP/3 server with a real certificate, verification
succeeds with no flag at all.

Closes [#77](https://github.com/zoxy-io/zrk/issues/77).

## Reads are batched, and it is worth about 40%

Linux generic receive offload coalesces consecutive datagrams of one flow into
a single buffer and reports the size they were segmented at. A 4 KiB response
is three or four datagrams; against a server that segments its sends, zrk now
reads them in one syscall instead of four.

Measured, 4 KiB bodies, `-c 2 -s 8 --closed`: **14,936 req/s without, 20,505
with** — and 3.30 datagrams per read rather than 1.00. It is inert wherever the
kernel or the peer declines, and costs 62 KiB per connection.

It is worth saying how that number was nearly missed, because the same trap is
waiting in any HTTP/3 benchmark. The first measurement said the feature did
*nothing*, and the reason was the rig: the target was reached through a
published container port, and Docker runs a `docker-proxy` for one of those — a
userspace relay that reads one datagram and writes one datagram, taking a
server's segmented burst apart before it arrives. **A benchmark path with a
userspace relay in it cannot see this feature at all.** The tell was a
coalescing ratio of exactly 1.00 at every rate tried; a real distribution is
never that clean.

## And a defect in the first version of it

The `UDP_GRO` control message carries an `int`, and the parser read sixteen
bits of it. That is correct on a little-endian machine by accident, which is
why the figure above is real — and on a big-endian one it reads zero, hands the
whole coalesced burst on as a single datagram, and every burst is then
discarded without a word until the connection is retired. Found in review;
fixed, along with a payload bound checked against the wrong object, two
guards that could wrap in the shipping build, and a truncated read that was
passed on rather than dropped.

The tests could not have caught any of it: the fixture built a control message
two octets wide *because the parser read two octets*, so the two agreed with
each other and with nothing else. It builds the kernel's layout now, verified
against a live socket.

## Still one datagram per syscall on the way out

Send-side batching is implemented and **not** merged. Measured, it is worth
about 2% on a send-heavy workload and slightly negative on a receive-heavy one,
because a QUIC client's egress is 60-to-70-octet packets and send syscalls are
not what bounds this. [#83](https://github.com/zoxy-io/zrk/issues/83) revisits
it for a path with real latency, which is the one case that could change the
answer — every measurement so far was over loopback, where responses trickle
back one at a time and a flush rarely has more than one datagram to send.

## Everything else

Unchanged from alpha.1: `-c`, the pacing and every latency number mean what
they mean on the other transports, and `--closed`, ramps, `--timeseries`, the
JSON summary and the CI gates all carry over.
