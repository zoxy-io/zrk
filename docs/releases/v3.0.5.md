zrk 3.0.5 keeps HTTP/3 connections open when a server repeats itself about a
request that has already finished. zrk 3.0.4 closed them, counted a read
error and reconnected, so the more a server retransmitted, the worse it
measured.

```sh
brew upgrade zrk
```

## Late frames for a finished request

A QUIC server can still be talking about a request after the client is done
with it. It sends the tail of a response again after a probe or a spurious
loss, or a flow-control update crosses the client's last acknowledgement.
RFC 9000 has the client discard such frames. zrk's HTTP/3 client took a frame
for one of its own streams that it no longer held for a stream it had never
opened, and closed the connection with STREAM_STATE_ERROR. Every request in
flight on it became a read error, and the connection was opened again.

A server retransmits more the closer it runs to saturation, so this charged
servers unevenly. On zoxy-io/benchmark's HTTP/3 profile, it was every HTTP/3
read error zrk logged against zoxy, while nginx, with the same client, saw
almost none.

## Verified

1,000 HTTP/3 connections at 3,000 requests/s for 40 s against zoxy held to
0.35 of a CPU, on Linux. With 3.0.4, each run logged 27 to 97 read errors,
every one of them this STREAM_STATE_ERROR. With 3.0.5 there were none, and
zoxy saw exactly 1,000 handshakes, so no connection was opened twice.

The HTTP/3 library is also cheaper per packet (zoxy-io/h3#10). Its buffers
move with `@memmove` instead of an octet at a time, and STREAM frames are
sized to fill each datagram exactly.

HTTP/1.1 and HTTP/2 are unchanged.
