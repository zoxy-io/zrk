The first release candidate for v3.0.0. Unless something turns up, this is
3.0.0: what changes between now and the stable tag is fixes, not features.

**This is a prerelease.** It is not on the Homebrew tap and `brew upgrade` will
not offer it — the tap holds one formula and stable users read it. Take an
archive from the assets below.

Before calling the alphas done, they were pointed at real servers rather than
the ones the test suite stands in for: Caddy (Go, all three protocols), nginx,
Google and Cloudflare. That turned up failures no test covered, and some were
not small. This release is those fixes, and one of them matters even if you
never touch `--http3` — it is in the HTTPS path every zrk since v2.4.0 has used.

## HTTPS against a Go server failed every request

Point zrk at Caddy, Traefik, a Go `net/http` service or most Go-based ingress
over HTTPS, on HTTP/1.1 or `--http2`, and every request failed. The handshake
succeeded. The first read after it did not.

Go's TLS stack sends a session ticket straight after the handshake, and its
ticket carries an empty nonce. RFC 8446 allows that — the field is
`ticket_nonce<0..255>` — but zssl, the TLS library underneath zrk, refused it
as malformed, and took the connection down with it. Fixed in
[zoxy-io/zssl#20](https://github.com/zoxy-io/zssl/pull/20), which this release
pins.

This was not new in 3.0: every zssl zrk has used since v2.4.0 refused it. If
you ever saw a wall of connect or read errors against a Go server and put it
down to the server, it was this.

## Fixes since alpha.3

| | alpha.3 | rc.1 |
| --- | --- | --- |
| HTTPS (HTTP/1.1, HTTP/2) against a Go server | 100% errors | 0 |
| `--http3 -b …` against a quic-go server (Caddy) | 100% errors, even for a 1-byte body | 0 |
| `--http2` response over 64 MiB, default `-s 1` | every request an error | 0 |
| `--http2 -b @3MB` against Go's HTTP/2 server | 5–19 of every 40 failed | 0 |

- **`--http3` with a request body.** A server may answer before it has read the
  whole request, then tell the client to stop sending with `H3_NO_ERROR`
  (RFC 9114 §4.1). quic-go does that after every handler that leaves the body
  unread. zrk counted it as a write error and threw away the response that was
  already on its way.
- **Large `--http2` responses.** The bound that protects a connection from an
  endless stream of frames was counting *every* frame, so it was really a bound
  on response size: 4,096 frames of 16 KiB. It counts frames that carry the
  response nowhere now. The multiplexed path already did.
- **`--http2` request bodies respect flow control.** zrk wrote a body straight
  through, ignoring the server's windows. A body over 64 KiB overran them, and a
  server that enforces them reset the stream. Now the body goes out as the
  windows allow and the rest as the server gives credit back.
- **A GOAWAY could drop requests the server had already accepted.** When a
  multiplexed HTTP/2 connection was refused a new stream, zrk marked the whole
  connection dead. The requests the server had already taken were then never
  waited for, and never counted. They finish now, as GOAWAY intends.
- **An `--http3` connection could stall at zero requests a second.** A stream
  whose request had expired was never read again. Streams are released in
  order, so it held back every stream behind it until no new request could
  open — no errors, just nothing. Its data is drained now, once the server says
  where the stream ends.
- **`--http3` counted one error too many** whenever a connection died: one per
  request in flight, then one more for the connection. It counts N for N now,
  as `--http2` does, so `--max-error-rate` means the same thing on both.

## When nothing works, zrk says so

Three ways a run could measure nothing and still look fine:

- **A run where no request succeeds now exits 1** and says why, instead of
  exiting 0 with a report of zeros. When connecting is all that failed, it names
  the first failure:

  ```
  zrk: no request completed; connecting failed: CertificateVerificationFailed (-k skips certificate verification)
  zrk: no request completed; connecting failed: AlpnH2Declined (the server does not speak HTTP/2 over TLS; drop --http2)
  zrk: no request completed; connecting failed: HandshakeTimeout (the handshake did not finish within --timeout)
  zrk: no request completed; connecting failed: ConnectionRefused (nothing is listening on that port)
  ```

- **The TLS handshake is bounded by `--timeout`.** A server that accepted the
  connection and never answered left the handshake waiting until the run ended,
  and the report showed no requests *and no errors*.
- **A multiplexed connection the server closes before it carries a request is
  counted**, and retried after a short pause. Before, zrk reconnected in a tight
  loop and recorded nothing.

**What this changes for you.** A script that ran zrk against a target it could
not reach and checked for exit 0 will now see 1. That is the point: 1 already
meant "the run failed", and a run that measured nothing failed.

## Known issues

- **`--http3` is slow on large responses over a real network.** Each stream's
  receive window is 16 KiB, so one stream moves at most 16 KiB per round trip.
  Over loopback that is invisible; at a 62 ms round trip, a 126 KB page takes
  about 700 ms against HTTP/2's 110 ms, and a 1.3 MB one runs past the default
  `--timeout`. Compare against `--http2` before trusting an `--http3` latency
  for a response beyond a few tens of KiB across a network.
  [#89](https://github.com/zoxy-io/zrk/issues/89).
- **An `--http3` connection quiet for twice `--timeout` is replaced.** zrk sends
  no keepalive yet, and a QUIC server drops an idle connection without telling
  the client, so a quiet connection is not trusted with the next request. At a
  rate low enough to leave connections that idle — a large `-c` at a small `-R`,
  or the bottom of a ramp — some requests carry a fresh handshake in their
  latency.
- **`--deadline-abort` can cut a request off late** on a non-multiplexed
  connection, when `--deadline` is much shorter than `--timeout` and the offered
  rate is low. Plain `--deadline` shedding is unaffected.
  [#73](https://github.com/zoxy-io/zrk/issues/73).
- **ECDSA test certificates made with macOS's `/usr/bin/openssl`** are refused
  by `--http3`, even with `-k`, as in alpha.3. Make them with OpenSSL 3.

`--http3` is described as experimental in the README rather than as a
prototype: it measures correctly, and the first two items above are the cases
where what it measures is partly zrk.

## For embedders

`h2conn` is exported from the library root, and three things in it changed:

- **`Session.beginStream` no longer writes the request body.** It sends the
  HEADERS and leaves the body pending, because how much may go out depends on
  the peer's flow-control windows. Drive it with `reserveBody` and `writeBody`
  as `credit` arrives (`bodyPending` says whether any is left), or call
  `exchange`, which does all of that.
- **`Incoming` has a new `window` variant**, for WINDOW_UPDATE. An exhaustive
  `switch` over it needs a case; pass it to `Session.credit`.
- **`connection.Counters` has a new field**, `first_connect_error`.

`runner.run`, which is what `docs/library.md` documents, is unchanged.

## Everything else

Unchanged from alpha.3: GOAWAY handling and retries, certificate verification on
`--http3`, receive batching, and every flag, report and gate. The changes are in
[#91](https://github.com/zoxy-io/zrk/pull/91).
